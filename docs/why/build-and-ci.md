# Why — the build, CI, and where code lives

## CI is two workflows, split by what they cost

- **`check`** runs on every push and PR: build, test, the recipe tests named individually so a
  contributor sees *which* gate they tripped, and clippy with `-D warnings`. No VM — every test
  here runs on a pure function, which is why the guest's configuration is generated by pure
  functions at all.
- **`image`** boots real VMs: it builds the base image and the layers for the recipes a PR
  touched, then runs one session per agent. `check` proves a recipe parses and declares sane
  things; only this proves it *installs*, because cloud-init does not abort on failure and the
  only honest answer comes from looking for the binary afterwards.

`image` also runs weekly, and that is not belt-and-braces: upstream breaks recipes with no commit
here. Antigravity's installer began serving its script gzipped, which turned `agy`'s `curl` into a
download of a binary; nothing but a scheduled build finds that.

The per-agent layer is what makes this affordable. A PR touching one recipe builds one layer, so a
broken or outdated recipe is one red job rather than an image nobody can finish building.

## A recipe's `install` is arbitrary root shell, and `image` runs it

That is the point, and it is also why the workflow uses `pull_request` and never
`pull_request_target`: a fork's job gets a read-only token and no secrets. Keep GitHub's "require
approval for all outside collaborators" setting on — without it, opening a PR here is a way to run
code on the runner.

## Why `cargo fmt` is not a gate

The layout is deliberate: some expressions are split so they read in one glance — the aligned `||`
in `has_credentials`, for instance — and rustfmt cannot tell a meaningful break from an accidental
one.

Measured, so the choice is not folklore: with no `rustfmt.toml` a bare `cargo fmt` touches 622
lines (+489/−133), mostly exploding method chains one call per line; `max_width = 100` with
`use_small_heuristics = "Max"` is the least invasive at 287 (+124/−163). Neither changes
behaviour — stripping whitespace leaves the files identical apart from redundant closure braces and
the order of `mod`/`use` declarations — but neither reads better either.

If this is ever revisited, it is one commit of nothing but formatting.

## Module boundaries are by subject, not convenience

The first split was cut by line ranges and put both cloud-init generators in `net.rs` and the whole
proxy server in `qemu.rs`; both were wrong and both were moved. If something feels misfiled it
probably is — move it rather than leaving a note.

**Every module holds its own tests.** They all lived in `main.rs`, which put a proxy failure in a
file that does not mention the proxy and grew the file past 3000 lines. A test belongs beside the
thing it tests: the YAML and the recipes in `guest.rs`, the allowlist and the lockdown in `net.rs`,
the image chain and the boot watch in `qemu.rs`, the recipes-as-data in `agents.rs`, the status
block in `ui.rs`. `main.rs` keeps the registry, the local config and the session's own scratch.

A few moved tests reach crate-root items that are private, which a child module may name but
`use crate::*` does not bring in, so those carry an explicit `use crate::<item>`. Where that list
grows, it is a signal the item is in the wrong file.

**The test count is the thing to check after a move, because a `#[test]` in a module that is not
declared does not fail — it disappears.**

## Recipes are files, not Rust strings

They were literals with `@NAME@` placeholders until every `{` in a shell script had to be doubled
to survive `format!`. The `#[ignore]`d `dump_generated_documents` test writes every generated guest
document to `/tmp/geli-baseline`: dump before a refactor, dump after, and diff. That is how the
module split, the move to file-based recipes, and the extraction of `execute_sandbox`'s pure parts
were each shown to change nothing.
